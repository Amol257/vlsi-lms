# VLSI LMS : Secrets Rotation Runbook & History Sanitization

This runbook documents the required procedures for rotating production secrets and sanitizing repository history.

> [!IMPORTANT]
> **Production Key Generation Rule**:
> Production must use an `APP_KEY` generated directly on the administrator's own workstation or server terminal using `openssl rand -hex 32`. Never use any key generated by an AI coding assistant, demo template, or committed code.

---

## 1. Secrets Inventory & Invalidation Scope

| Secret Key | Config Key | Generation Command | Impact of Rotation |
|---|---|---|---|
| **LMS Root App Key** | `app.app_key` | `openssl rand -hex 32` | Invalidates active user session cookies, revokes all timed HLS playback tokens, and requires re-encrypting or re-importing video keys in `videos.key_enc`. |
| **Enrollment Webhook Secret** | `enrollment.webhook_secret` | `openssl rand -hex 32` | Blocks external course provisioning until updated simultaneously on `vlsiinsights.com`. |
| **Razorpay Webhook Secret** | `razorpay.webhook_secret` | Obtained from Razorpay Dashboard | Blocks Razorpay automated payment capture until updated in Razorpay Webhook settings. |
| **MySQL Password** | `db.pass` | Generated in Hostinger Panel | Immediate disconnection until `config.local.php` is updated. |

## 2. Secrets Rotation Procedure

### Step 1: Generate New Secrets
Execute the following on a secure terminal:
```bash
# Generate 64 hex characters (32 bytes) for APP_KEY
openssl rand -hex 32

# Generate 64 hex characters for Webhook Secret
openssl rand -hex 32
```

### Step 2: Update `config.local.php`
Place the newly generated secrets into `config.local.php` (stored one level above the document root, e.g. `/home/u123456789/config.local.php`):
```php
'app' => [
    'app_key' => '<NEW_64_HEX_CHARS_GENERATED_BY_ADMIN>',
    // ...
],
'enrollment' => [
    'webhook_secret' => '<NEW_64_HEX_CHARS_WEBHOOK_SECRET>'
]
```

### Step 3: Purge Live Database Sessions & Demo Accounts
Run these queries in phpMyAdmin or MySQL CLI:
```sql
-- Terminate all existing student device sessions
TRUNCATE TABLE lms_active_session;

-- Invalidate previous rate limit counters
TRUNCATE TABLE rate_limits;

-- Permanently block or delete legacy demo accounts
UPDATE lms_users SET status = 'blocked' 
WHERE email IN ('admin@lms.local', 'teacher@vlsiinsights.com', 'student@example.com');
```

## 3. Git History Sanitization Commands

Any secret committed in earlier Git commits must be treated as permanently compromised. To purge the legacy key from historical commits before publishing:

### Option A: Using git-filter-repo (Recommended)
```bash
# 1. Create a clean mirror clone
git clone --mirror https://github.com/Amol257/vlsi-lms.git lms-cleanup
cd lms-cleanup

# 2. Set the leaked key in a local shell variable (do not hardcode in scripts)
LEAKED_KEY="<PASTE_COMPROMISED_KEY_HEX_HERE>"

# 3. Replace the exposed key string across all commit history
git filter-repo --replace-text <(echo "${LEAKED_KEY}==><64_HEX_CHARS_GENERATED_BY_ADMIN>")

# 4. Force push the rewritten history back to origin
git push --force --all origin
git push --force --tags origin
```

### Option B: Using BFG Repo-Cleaner
```bash
# 1. Place the leaked key in a temporary file
echo "<PASTE_COMPROMISED_KEY_HEX_HERE>" > passwords.txt

# 2. Run BFG on a bare or mirror clone
java -jar bfg.jar --replace-text passwords.txt lms-cleanup.git

# 3. Reflog expiration and force push
cd lms-cleanup.git
git reflog expire --expire=now --all && git gc --prune=now --aggressive
git push --force --all origin
rm passwords.txt
```

## 4. Enabling GitHub Secret Scanning and Push Protection

To prevent any future credentials or keys from being pushed to the repository:

1. Navigate to the repository on GitHub: `https://github.com/Amol257/vlsi-lms`.
2. Click on the **Settings** tab.
3. In the left sidebar, navigate to **Code security and analysis** (under the "Security" section).
4. Locate **Secret scanning**:
   - Click **Enable** for *Secret scanning*.
5. Locate **Push protection**:
   - Click **Enable** for *Push protection*.
6. Push protection will immediately intercept and block any commit containing recognized secrets, tokens, private keys, or API credentials before they reach GitHub.
